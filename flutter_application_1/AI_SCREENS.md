# AI generation and results

Screens 10 and 11 extend the existing `AiProcessingScreen` and `AiResultScreen`.
Reference artwork is in `references/`. Shared theme, step indicator, buttons and
bottom navigation are reused. `DesignScreenLayout` now accepts optional bottom
navigation; `HomeScreen.initialTab` allows returning directly to a destination.

## Try the workflow

Start the existing FastAPI backend using `backend/README.md`, then launch Flutter
with `flutter run --dart-define-from-file=.tools/flutter-local.json`. For an Android
emulator, configure the API URL as `http://10.0.2.2:8000` in an ignored local config.
Use the backend development token; never commit credentials.

Upload a room, confirm its type, select style/budget, and enter the existing mask
editor. Generate from there. The processing screen polls `/api/jobs/{id}` every
two seconds and only opens results after `completed` and an output-image fetch.
Stop/back cancels the actual job. Network retry resumes a nonterminal job rather
than deliberately creating another one. Failed/cancelled jobs can be resubmitted.
No fixed duration, simulated progress or demo result is used.

On results, drag across the image or use the accessible slider below it. Original
bytes remain separate from generated bytes. Test regenerate, edit, save, furniture,
bottom destinations, image export and earlier-result history. Try a narrow Android
viewport and larger system fonts; screen bodies scroll.

Disconnect the backend during polling to check error/retry. Disable/uninstall model
weights to check the existing explicit unavailable error. Generation requires the
backend's enabled, installed diffusion models; this UI does not bypass that check.

## Backend data still needed

The existing backend implements upload, generation, polling, cancellation, image
storage and project persistence. Model availability depends on deployment.
It does not currently provide a furniture catalog matched to generated images,
verified prices, generated room titles/descriptions, or room-recognition stages.

The optional result metadata contract is `job.parameters`:

```json
{
  "room_name": "Миний зочны өрөө",
  "description": "Тохижуулалтын тайлбар",
  "structure_recognized": true,
  "furniture_removed": true,
  "furniture": [
    {"name": "Буйдан", "quantity": 1, "unit_price_mnt": 1200000}
  ]
}
```

These values must describe actual work and catalog data. Until supplied, room
name/style use selected preferences, the description uses the submitted prompt,
and furniture count, price and savings explicitly remain unknown. The furniture
screen explains missing data. Counts sum quantities; totals sum quantity × unit
price; savings are budget minus total, with over-budget amounts labelled separately.
Missing/malformed/partially priced catalog data never becomes a fabricated price.
Checkmarks require confirmed metadata or the existing cleaned-image state.

The generation API already exists, so an alternate demo implementation was not
introduced. Automated tests use isolated API doubles only.
